# CoverMate: Copy Review and Voice Direction

วันที่ตรวจ: 27 กันยายน 2026

สถานะ: ปรับข้อความต้นทางและ CMS default seeds แล้ว พร้อมฉบับร่างและเว็บพรีวิวในเครื่อง ยังไม่ได้เขียน CMS บนระบบจริง, push หรือ deploy

## ผลการปรับข้อความ

- เปลี่ยนข้อความทั้งไทยและอังกฤษใน Home, Motor, FAQ ทั้ง 9 ข้อ, รายละเอียดบริการ, ตรวจกรมธรรม์, ติดต่อ/ต่ออายุ, ค่าปรึกษาและค่าตอบแทน, ท้ายเว็บ, SEO และข้อความ UI บทความที่ยังปิดอยู่
- ย่อคำตอบ FAQ ให้ตอบคำถามโดยตรง เอาเวลาอ่านบทความเดิมออกจากคำตอบสั้น และลดคำโปรยตกแต่งที่ซ้ำกัน เหลือข้อความแบรนด์ใน Hero
- ไม่เปลี่ยนลิงก์, รูป, ใบอนุญาต, IDs, ลำดับ/การเปิดปิดส่วนต่าง ๆ, ค่าความคุ้มครองในตาราง, topic options, เงื่อนไขยินยอม หรือเนื้อหาบทความที่ลูกค้าเขียนเอง
- เว้นข้อกำหนดสิทธิข้อมูลส่วนบุคคลและระยะเวลาเก็บข้อมูลไว้สำหรับตรวจนโยบายแยก ไม่ถือว่างานนี้เป็น legal/compliance audit
- ชุดข้อความที่ใช้จริง: `scripts/lib/copy-voice-20260927.mjs` ส่วนตารางข้อเสนอด้านล่างเป็นบันทึกก่อนลงมือ ข้อความสุดท้ายอาจปรับให้กระชับขึ้น
- การสร้างร่างใช้ published state ที่อ่านมาใน `uat-results/copy-audit-20260927/source-state.json` และเก็บทั้ง config/text โดยไม่มี remote writes
- `copy-proposal.json` เก็บค่าเก่า/ใหม่เป็นราย field ด้วย stable CMS IDs; `copy-draft.json` เป็นฉบับพรีวิว ห้ามนำทั้งไฟล์ไปทับ CMS draft ปัจจุบันโดยไม่ตรวจงานค้าง
- เมื่อต้องการนำขึ้น CMS ให้ใช้ `applyCopyProposal` กับ state ที่อ่านใหม่ และหยุดเมื่อ copy field หรือ inline override เปลี่ยนจาก baseline ไม่เขียนทับงานที่แก้ระหว่างทาง การ deploy โค้ดอย่างเดียวไม่เปลี่ยน published CMS copy

### การตรวจรอบนี้

- ตรวจ source/default seed parity, patch idempotence, field conflicts, การคงข้อมูลนอกขอบเขต และการจับ row ด้วย ID หลังเรียงรายการใหม่
- ตรวจ Home/Motor ทั้ง TH/EN ที่ 1440px และ 390px: กด FAQ ครบทุกข้อ, headings, metadata, optional blank slogans และ horizontal overflow
- รูปหลังแก้และผลตรวจอยู่ใน `uat-results/copy-audit-20260927/` พรีวิวปิดการส่งฟอร์มและการเขียนข้อมูลทุกชนิด
- เทสต์ CMS ownership ปรับให้ยอมรับคำโปรยว่างอย่างตั้งใจ ส่วน FAQ browser harness เพิ่มการกดยืนยัน Save draft ตาม dialog ที่มีอยู่แล้ว ไม่เปลี่ยนพฤติกรรมบันทึกจริง
- ผ่าน `check:contracts`, `check:cms`, `check:faq` (รวมบันทึกร่าง/โหลดใหม่/พรีวิวใน fixture), `check:contact`, `check:seo`, `check:errors`, `check:visitor-source`, `copy-voice-check`, `copy-voice-browser-check` และ `git diff --check`
- ไม่ทดสอบ production writes, email delivery หรือ blog publishing ในงานปรับสำนวนนี้

### ไฟล์และคำสั่งสำหรับทำต่อ

ทำจาก checkout ที่ระบุใน [HANDOFF.md](HANDOFF.md) ไม่ย้ายงานไป root checkout
หรือถือว่าพอร์ตพรีวิวเก่ายังเปิดอยู่ ไฟล์ใน `uat-results/` เป็นหลักฐานในเครื่อง
และไม่ได้ติดตามด้วย Git

- `scripts/lib/copy-voice-20260927.mjs`: ข้อความที่ปรับแล้ว พร้อม canonical owner และ fallback source path
- `scripts/prepare-copy-voice-20260927.mjs`: สร้าง proposal/preview จาก baseline ที่ใช้ตรวจ และ export `applyCopyProposal(state, proposal)` ซึ่งไม่มี remote I/O
- `scripts/copy-voice-preview.mjs`: เปิด Home/Motor แบบอ่านอย่างเดียว ปิด Admin, API และการส่งฟอร์ม ไม่ใช่พรีวิวสำหรับทดสอบ CMS
- FAQ เพิ่ม/ลบเป็นงานแยกจากสำนวน อ่าน [วงจร FAQ ใน CMS](CMS_CONTENT_OWNERSHIP.md#faq-collection-editing); ไม่ใช้ copy proposal เพิ่ม/ลบคำถาม

ตรวจเฉพาะ source/default ได้โดยไม่ใช้ snapshot:

```bash
node scripts/copy-voice-check.mjs
```

เมื่อยังมี baseline และร่างที่ใช้ตรวจรอบนี้อยู่:

```bash
node scripts/copy-voice-check.mjs uat-results/copy-audit-20260927/source-state.json
node scripts/copy-voice-preview.mjs uat-results/copy-audit-20260927/copy-draft.json
```

คำสั่งพรีวิวจะแสดง URL และพอร์ตจริง ส่วน
`node scripts/copy-voice-browser-check.mjs` ใช้ร่างดังกล่าวตรวจ Home/Motor
TH/EN บน desktop/mobile ไม่ต้องรันซ้ำสำหรับการแก้เอกสารอย่างเดียว

ก่อนนำข้อความเข้า CMS ต้องอ่าน state ล่าสุดและใช้ **proposal ที่ผ่านการตรวจแล้ว**
กับ `applyCopyProposal` หยุดเมื่อค่าเดิม, inline override หรือ owner เปลี่ยน/หายไป
อย่าสร้าง baseline ใหม่เพื่อทำให้ conflict หาย และอย่าเอา stable IDs จากรอบนี้ไป
จับรายการด้วยเลขลำดับ หาก baseline/proposal หาย ให้ตรวจเทียบข้อมูลใหม่ก่อนทำต่อ
การเขียน Draft และ Publish ยังต้องผ่าน workflow ปกติและได้รับอนุญาตตามขอบเขต
เพราะ Publish อาจพางานอื่นใน Draft ออกไปด้วย

## 1. ทิศทางที่ผู้ใช้ต้องการ

ให้รู้สึกเหมือนเพื่อนร่วมทาง มากกว่านักการตลาด: พูดเรียบง่าย สุภาพ จริงจังกับข้อมูล และช่วยตอบเรื่องที่คนอ่านกำลังสงสัย ความเป็นกันเองควรมาจากวิธีอธิบายและความช่วยเหลือที่ชัดเจน ไม่ใช่คำประกาศว่าเราอบอุ่นหรือจริงใจ

FAQ ต้องเป็นคำถามที่คนธรรมดาน่าจะถามจริง ไม่ใช่หัวข้อบทความหรือ punchline ที่เปลี่ยนท้ายประโยคเป็นคำถาม ไม่จำเป็นต้องมีสโลแกนในทุกส่วนของหน้า และไม่ต้องนำคำว่า "เพื่อนร่วมทาง" ไปสร้างสโลแกนใหม่

## 2. ขอบเขตและหลักฐาน

- อ่านหน้าเว็บจริงและ published CMS configuration ของ Home และ Motor ทั้งไทยและอังกฤษ: `/`, `/?lang=en`, `/motor`, `/motor?lang=en`
- ครอบคลุมข้อความหลัก บริการ ตรวจกรมธรรม์ ตารางเปรียบเทียบ FAQ ติดต่อ ต่ออายุ ค่าตอบแทน ความเป็นส่วนตัว ใบอนุญาต ท้ายเว็บ และข้อความสถานะฟอร์ม
- อ่านรายละเอียดบริการจาก configuration เพิ่มเติม เพราะ accordion บริการเปิดได้ทีละรายการ
- ตรวจข้อความ UI บทความจาก configuration เท่านั้น โมดูลบทความฝั่งสาธารณะปิดอยู่ขณะตรวจ ไม่ได้อ้างว่าอ่านบทความที่เผยแพร่จริงครบแล้ว
- ข้อมูลจับจาก production เวลา `2026-09-27T14:12:10.030Z` อยู่ใน `uat-results/copy-audit-20260927/live-copy.json` ไม่มีการส่งฟอร์มหรือเขียนข้อมูล CMS
- รอบนี้ไม่รวมการเปลี่ยนดีไซน์ การทดสอบทุก flow อีเมล โปสเตอร์ ข้อความ Admin หรือการรับรองความถูกต้องด้านประกัน ภาษี และกฎหมายทั้งเว็บไซต์

## 3. สิ่งที่พบก่อนปรับ

ส่วน 3-12 เก็บผลวิจัยและข้อเสนอก่อนลงมือ ไม่ใช่รายการงานที่ยังไม่ได้ทำทั้งหมด
ให้ใช้ส่วน "ผลการปรับข้อความ" ด้านบนและชุดข้อความใน source เป็นสถานะล่าสุด

### ภาษาเน้นสร้างความรู้สึกมากกว่าตอบคำถาม

พบคำอย่าง "ตามจังหวะของคุณ", "มากกว่าการขาย", "ทางเลือกที่ใช่" และข้อความเรื่องความเข้าใจ/ความจริงใจซ้ำหลายส่วน บางประโยคไม่ได้เพิ่มข้อมูลว่าช่วยอะไรได้จริง ตัดออกได้โดยไม่ต้องหาสโลแกนใหม่มาแทน

### รายละเอียดบทบาทถูกอัดไว้ในประโยคยาว

ข้อความเรื่องตัวแทน AIA และนายหน้ารถยนต์ผ่านศรีกรุงโบรคเกอร์จำเป็นต้องชัด แต่ไม่จำเป็นต้องใช้สำนวน "ดำเนินการผ่าน" หรืออธิบายทุกบทบาทในประโยคเดียว ควรแยกประโยคหรือแยกตามประเภทบริการ ไม่ลบความแตกต่างระหว่างตัวแทน นายหน้า และบริษัทผู้รับประกัน

### FAQ ผสมคำถามบริการกับหัวข้อบทความ

ใน published configuration มี FAQ บริการ 5 รายการ และอีก 4 รายการมี `sourceGuideId` พร้อมเวลาอ่านและคำตอบยาว หัวข้อกลุ่มหลังเป็นการบอกข้อสรุปหรือสร้างความสนใจ ไม่ใช่คำถามจากลูกค้า จึงอ่านเหมือนคอนเทนต์โฆษณาปะปนกับคำถามทั่วไป

การเปลี่ยนเฉพาะหัวข้อยังไม่พอ ต้องย่อคำตอบให้ตอบเรื่องนั้นก่อนด้วย เนื้อหายาวอาจแยกไปเป็นบทความภายหลัง แต่ต้องมีบทความที่เผยแพร่จริงก่อนเพิ่มลิงก์อ่านต่อ

### ย้ำว่าไม่ขายหรือไม่ตามมากเกินไป

การบอกนโยบายติดตามและค่าบริการอย่างชัดเจนมีประโยชน์ แต่ไม่ควรย้ำทุกส่วนว่าไม่ขาย ไม่เร่ง ไม่โทรตาม หรือไม่มีเหตุผลจะเชียร์ การบอกขั้นตอนจริงช่วยสร้างความเชื่อใจได้มากกว่าคำยืนยันซ้ำ ๆ

### อังกฤษมีทั้งภาษาทางการและภาษาพูดที่ไม่เป็นธรรมชาติ

มีการสลับ `I/my` กับ `we/our` และสำนวนอย่าง `debt plus time`, `chasing things for you`, `what needs nothing`, `while the difference is limited` ควรเขียนอังกฤษใหม่ตามความหมาย ไม่แปลโครงประโยคไทยตรงตัว

### บางจุดเป็นประเด็นข้อเท็จจริง ไม่ใช่แค่สำนวน

คำอย่าง "ทุกบริษัท", "เท่ากันทุกบาท", "จบทุกค่าใช้จ่าย", "ทันทีที่ตรวจเจอ" และ "ไม่ปล่อยให้ขาด" ต้องตรวจขอบเขตจริงก่อนใช้ ภาษาที่นุ่มขึ้นแต่ยังสัญญาเท่าเดิมไม่ได้แก้ปัญหานี้

## 4. สิ่งที่เรียนรู้จากเว็บอื่น

ข้อสังเกตต่อไปนี้เป็นการอ่านตัวอย่าง ไม่ใช่ผลวิจัยผู้ใช้หรือข้อสรุปว่าเว็บไซต์ประกันทั้งหมดควรเขียนเหมือนกัน

- **Roojai:** FAQ หลายข้อเริ่มจากเรื่องที่ผู้ใช้ต้องทำ เช่น ติดต่อ ซื้อ และตรวจสถานะ แล้วตอบเป็นขั้นตอน นำโครงสร้างคำถามและคำตอบมาเป็นแนวทางได้ โดยไม่ต้องนำคำโฆษณาราคาหรือคำรับประกันของแบรนด์มาใช้ด้วย [อ่าน FAQ ของ Roojai](https://www.roojai.com/faq/)
- **LifeSearch:** อธิบายงานที่ปรึกษาผ่านการรับฟัง อธิบาย และช่วยเหลือลูกค้า เป็นตัวอย่างของการบอกว่าทำอะไรให้ แต่หน้าเว็บก็ยังมีสโลแกนของตัวเอง จึงควรเลือกเรียนรู้เฉพาะส่วนที่เป็นพฤติกรรมและบริการที่ชัดเจน [อ่านแนวทางบริการของ LifeSearch](https://www.lifesearch.com/about)
- **MoneyHelper:** อธิบายทั้งเหตุผลที่อาจต้องมีประกันและสถานการณ์ที่อาจไม่จำเป็น พร้อมชวนตรวจความคุ้มครองที่มีอยู่แล้ว เหมาะใช้เป็นแนวทางเนื้อหาที่ช่วยพิจารณาก่อนซื้อ ไม่ใช่ตั้งต้นว่าทุกคนต้องซื้อเพิ่ม ทั้งนี้เป็นบริบทสหราชอาณาจักร ไม่ใช้รายละเอียดผลิตภัณฑ์ ภาษี หรือกฎหมายของแหล่งนี้แทนข้อมูลไทย [อ่านตัวอย่างบทความของ MoneyHelper](https://www.moneyhelper.org.uk/en/everyday-money/insurance/what-is-life-insurance)

ข้อเสนอสำหรับ CoverMate: ใช้คำถามที่เข้าใจง่ายแบบหน้าบริการ อธิบายงานที่ช่วยได้อย่างชัดเจน และให้พื้นที่กับกรณีที่ลูกค้าอาจไม่ต้องเปลี่ยนหรือซื้อเพิ่ม โดยยังเปิดเผยบทบาทและค่าตอบแทนตามจริง

## 5. กติกาภาษา

1. **เริ่มจากเรื่องที่คนอ่านอยากรู้** เช่น "มีประกันอยู่แล้ว ให้ช่วยดูได้ไหม?" ไม่เริ่มจากข้อคิดหรือข้อสรุปแทนคนอ่าน
2. **ใช้คำทั่วไป แต่ไม่ลดความแม่นยำ** คำถามใช้ "ไหม", "ยังไง", "เท่าไหร่" ได้ คำตอบใช้ "กรมธรรม์", "ทุนประกัน", "ข้อยกเว้น" เมื่อจำเป็นและอธิบายคำที่คนอาจไม่คุ้น
3. **บอกสิ่งที่ช่วยได้เป็นงานจริง** เช่น ช่วยอ่านกรมธรรม์ อธิบายเงื่อนไข เทียบแผน และตรวจเอกสาร ไม่ใช้คำว่า "ดูแลทุกช่วงชีวิต" แทนรายละเอียดเหล่านี้
4. **อบอุ่นได้โดยไม่ต้องเล่นคำ** ไม่ใส่ "ครับ/ค่ะ" ทุกประโยค ไม่แสร้งสนิท ไม่ใช้คำย่อแชต และไม่ต้องลงท้ายทุกคำตอบด้วยการชวนซื้อหรือทัก LINE
5. **ใช้เสียงแบรนด์ให้สม่ำเสมอ** เสนอใช้ "เรา" และ `we` ทั้งเว็บ ใช้ "ผม" หรือ `I` เฉพาะข้อความที่ระบุผู้พูดชัดเจน ไม่เรียกตัวเองว่า "ทีม" ถ้าไม่ได้เป็นทีมจริง
6. **สโลแกนไม่ใช่ข้อบังคับ** FAQ ฟอร์ม ตาราง ค่าบริการ และคำอธิบายเงื่อนไขไม่ต้องมี punchline จุดแนะนำแบรนด์อาจมีประโยคสั้นหนึ่งจุดได้ แต่ต้องมีประโยชน์จริงและไม่พูดซ้ำทุกส่วน
7. **แยกความมั่นใจออกจากคำรับประกัน** คำตอบต้องระบุเงื่อนไขที่มีผลต่อเรื่องนั้น ไม่ใช้คำว่า "ตามเงื่อนไข" ท้ายทุกย่อหน้าเพื่อกลบคำสัญญาที่แรงเกินไปด้านหน้า

ข้อยกเว้นเรื่องสรรพนาม: ข้อความยินยอมและข้อความที่ร่างให้ลูกค้าส่งเขียนจากมุมลูกค้า จึงใช้ `I/my` ได้ ไม่ใช่จุดที่ต้องแทนด้วย `we/our` การตรวจต้องดูว่าใครเป็นผู้พูด ไม่ใช่ค้นหาและแทนที่ทั้งเว็บไซต์

## 6. ตัวอย่าง FAQ ที่เสนอ

เป็นตัวอย่างการเขียน ไม่ได้อ้างว่าเป็นคำถามจากประวัติการสนทนากับลูกค้าจริง และยังไม่ได้เผยแพร่

ข้อควรระวัง: "ช่วยดูกรมธรรม์" กับ "ย้ายผู้ดูแลกรมธรรม์" เป็นคนละบริการ หากเปลี่ยนหัวข้อเป็นการขอให้ช่วยดู ต้องไม่ทำให้ข้อมูลการย้ายผู้ดูแลเดิมหายไป ควรแยกเป็นคำถาม "อยากเปลี่ยนคนดูแลกรมธรรม์ ต้องทำยังไง?" และตรวจขั้นตอนจริงของแต่ละประเภทก่อนเขียนคำตอบ

หัวข้อส่วนนี้ใช้เพียง "คำถามที่พบบ่อย" ก็เพียงพอ ไม่ต้องมี kicker "คำถามที่ถูกถามบ่อย" ซ้ำอีกบรรทัด

### รูปแบบคำตอบ

ตอบให้ตรงคำถามในประโยคแรก ตามด้วยสิ่งที่ช่วยได้และเงื่อนไขที่จำเป็น หากยาวให้แยกย่อหน้าหรือรายการ ไม่จบด้วยสโลแกน ไม่ขยายไปชวนซื้อสินค้าที่ไม่ได้ถาม

ตัวอย่างร่างสำหรับบริการตรวจกรมธรรม์เดิม:

> ได้ เราช่วยอ่านกรมธรรม์เดิมและอธิบายว่าคุ้มครองอะไรบ้างได้ โดยไม่จำเป็นต้องซื้อประกันใหม่กับเรา ส่วนการเปลี่ยนผู้ดูแลกรมธรรม์เป็นอีกเรื่องหนึ่ง ต้องตรวจขั้นตอนกับบริษัทประกันก่อน

ตัวอย่างนี้ต้องให้เจ้าของยืนยันขอบเขตบริการก่อนเผยแพร่ การขอเอกสารในขั้นถัดไปต้องคงแนวทางปกปิดและส่งข้อมูลส่วนบุคคลของเว็บไซต์ ไม่ควรขอข้อมูลสุขภาพหรือบัตรประชาชนใน FAQ สาธารณะ

## 9. ข้อความที่ต้องตรวจข้อเท็จจริงก่อนแก้และเผยแพร่

รายการนี้เป็นจุดที่ควรยืนยัน ไม่ใช่ข้อสรุปทางกฎหมายหรือการรับรองว่าข้อความเดิมผิดทุกกรณี

| ข้อความ/ประเด็นที่พบ | ต้องยืนยันอะไร |
| --- | --- |
| "เบี้ยเท่ากันทุกบาท", "ไม่แพงกว่า", "ราคาไม่ต่างกัน" | แผน เงื่อนไข ช่องทาง โปรโมชั่น และค่าบริการที่กำลังเปรียบเทียบ ห้ามใช้ข้อสรุปแบบครอบจักรวาลโดยไม่มีหลักฐาน |
| "ทุกบริษัทในรอบเดียว" | บริษัทและแผนที่มีให้บริการจริง รวมถึงข้อจำกัดของรถและผู้ขอประกัน ไม่ทำให้เข้าใจว่าเสนอได้ทั้งตลาด |

| "รับเงินก้อนทันทีที่ตรวจพบ" / `the day ... diagnosed` | นิยามโรค เกณฑ์การจ่าย และกระบวนการพิจารณา ไม่ใช้คำบอกความเร็วที่ยังไม่ยืนยัน |

## 10. สิ่งที่ไม่ต้องรื้อ

- "วันนี้อยากให้ช่วยเรื่องไหน", "ชื่อที่ให้เรียก", "ส่งคำถามถึงเรา" และ "มีเรื่องไหนให้ช่วยดูไหม?" เป็นภาษาที่เข้ากับทิศทางนี้อยู่แล้ว

- ฟอร์มต้องแยกสถานะได้รับคำขอแล้ว / ส่งไม่สำเร็จ / ยังยืนยันไม่ได้ตามจริง ไม่เปลี่ยนทุกสถานะเป็นข้อความปลอบใจที่ทำให้เข้าใจว่าบันทึกแล้ว

4. อัปเดต published CMS ด้วย workflow ปกติหลังได้รับคำสั่งให้เผยแพร่ พร้อมปรับ source defaults ที่เป็น fallback ไม่แก้เพียงไฟล์ default แล้วถือว่าเว็บจริงเปลี่ยนแล้ว
5. ใช้ stable section/item IDs ของข้อมูลเดิม ไม่ bulk reset configuration ไม่เปลี่ยน contact links, licence numbers, form option IDs หรือเนื้อหาที่เจ้าของแก้ไว้นอกขอบเขต
6. ตรวจไทยและอังกฤษหลังเผยแพร่เฉพาะจุดที่แก้ รวมทั้งการตัดบรรทัดบนมือถือ โดยไม่สรุปว่าทั้งเว็บผ่านการทดสอบจากงานปรับภาษา

เจ้าของข้อความหลัก: `sections` (ระบุด้วย section/item ID), `motorPage`, `homeDesign`, `lineContact`, `contactSubmission`, `publicCopy`, `footer`, `articlesPage`, `articleDetail` ตามรายละเอียดใน `docs/CMS_CONTENT_OWNERSHIP.md`

บันทึกช่วงวิเคราะห์: ตอนเขียนข้อเสนอส่วนนี้ยังไม่ได้แก้ source ต่อมาได้ปรับ source
และทดสอบร่างในเครื่องตามสรุปด้านบนแล้ว ยังไม่มี commit, push, deploy หรือเขียน CMS จริง

### 12.6 ข้อความแนะนำเว็บในผลค้นหา

Home ที่เปิดจริงใช้ประโยค Hero เดิมเป็น `meta description` จึงมีสำนวน "ชีวิตและสุขภาพดำเนินการผ่าน AIA..." อยู่ด้วย แม้จะปรับข้อความบนหน้าแล้ว ต้องตรวจ metadata อีกครั้ง ไม่ถือว่าแก้ตามกันโดยอัตโนมัติ

ใน `motorPage.seo.description` ที่จัดเก็บไว้ พบคำอธิบายขึ้นต้น "หน้าเฉพาะประกันรถยนต์ของ CoverMate" และ `Dedicated motor insurance page from CoverMate` ซึ่งบอกโครงสร้างเว็บมากกว่าข้อมูลที่คนค้นหาต้องการ อีกทั้งจบที่ "และเงื่อน" / `and key co` เป็นข้อความตัดค้างในข้อมูลต้นทาง ไม่ใช่ข้อสรุปว่า Google ตัดข้อความแบบนั้น

ร่างสำหรับใช้ตรวจต่อ:

- **Home TH:** CoverMate ให้คำปรึกษาประกันชีวิตและสุขภาพ AIA พร้อมช่วยอ่านกรมธรรม์เดิมและเปรียบเทียบประกันรถยนต์ผ่านศรีกรุงโบรคเกอร์
- **Home EN:** Advice on AIA life and health insurance, help reviewing existing policies, and car insurance comparisons through Srikrung Broker.
- **Motor TH:** เปรียบเทียบเบี้ยและความคุ้มครองประกันรถยนต์กับ CoverMate พร้อมอธิบายเรื่องซ่อมห้าง ซ่อมอู่ และค่าเสียหายส่วนแรก
- **Motor EN:** Compare car insurance premiums and cover with CoverMate, with help understanding repair options, excess and policy terms.

ยังต้องตรวจข้อจำกัดความยาวของ editor และ metadata ที่ render หลังแก้ ไม่ตัดประโยคกลางคำเพื่อให้พอดีจำนวนอักษร ไม่เพิ่มจำนวนบริษัทหรือคำรับประกันราคาในข้อความค้นหาเอง

### 12.7 ข้อความที่ยังปิดอยู่: ตรวจให้พร้อมก่อนเปิด

พบ `on: false` ใน `how`, `claim`, `fit`, `voices` ข้อความด้านล่างจึงต้องแยกจากปัญหาภาษาที่ผู้เข้าชมกำลังเห็น

- **ขั้นตอนบริการ:** "ไม่ต้องเตรียมเอกสารใด ๆ" กว้างเกินขั้นถามเบื้องต้น ควรระบุ "เริ่มจากบอกเรื่องที่อยากสอบถาม หากต้องใช้เอกสารเพิ่มเติม เราจะแจ้งให้ทราบ" ไม่รับปากว่าการเสนอราคา/เคลมทุกกรณีไม่ต้องใช้เอกสาร
- **เครื่องคำนวณ:** มี "ตรวจ health limit แยกจากทุนชีวิต", "room gap", "ทุนชีวิตที่ควรเริ่มจาก" และ `Life need starting point` ที่ฟังเป็นภาษาภายใน ควรอธิบายแยกเป็น "วงเงินประกันสุขภาพ", "ส่วนต่างค่าห้องโดยประมาณ" และ "ความคุ้มครองชีวิตที่คำนวณได้เบื้องต้น" พร้อมคงข้อจำกัดของการประมาณ ไม่เรียกผลคำนวณว่าแผนที่แนะนำให้ซื้อ
- **ข้อความที่ส่งต่อจากเครื่องคำนวณ:** `publicCopy.consultationSummary` ใช้ "ทุนชีวิตที่ควรมีประมาณ" ควรระบุว่าเป็น "ผลประเมินความคุ้มครองชีวิตเบื้องต้น" เพื่อไม่เปลี่ยนตัวเลขอ้างอิงให้เป็นคำแนะนำเฉพาะบุคคล และต้องเก็บ placeholders เดิม
- **รีวิว:** ยังเป็นช่องสำหรับใส่รีวิวจริง ไม่เขียนคำรับรองปลอมเพื่อให้ดูอบอุ่น และไม่อ้างว่ารีวิวตัวอย่างกำลังเผยแพร่อยู่
- **คำแนะนำเมื่อเกิดอุบัติเหตุ:** ข้อความอย่าง `for when you cannot think straight` และ "ตอนนั้นไม่มีใครคิดเป็นขั้นตอน" คาดเดาสภาพผู้อ่านและอาจทำให้รู้สึกถูกตำหนิ ใช้ชื่อเรื่องตรง ๆ เช่น "เมื่อเกิดอุบัติเหตุรถยนต์" และทบทวนเนื้อหาฉุกเฉินต่างหากจากโทนภาษา

**แยกเป็นประเด็นความปลอดภัยก่อนเปิด:** `motorPage.hero.claimText` มี "โทร 1669 ก่อนเสมอ" และส่วน `claim` ชวนโทรหา CoverMate ก่อนแจ้งบริษัท ขณะตรวจไม่พบข้อความ Hero ฉุกเฉินนี้ในข้อความหน้ารถยนต์ที่ render และส่วน claim ปิดอยู่ แต่ไม่ควรเปิดกลับมาโดยใช้คำเดิม

1669 เป็นช่องทางการแพทย์ฉุกเฉินตาม [ข้อมูลของสถาบันการแพทย์ฉุกเฉินแห่งชาติ](https://www.niems.go.th/1/Ebook/Detail/8476?group=22) จึงควรเขียนขอบเขตให้ชัด เช่น "หากมีผู้เจ็บป่วยฉุกเฉิน โทร 1669" ไม่วาง CoverMate เป็นด่านก่อนรับความช่วยเหลือฉุกเฉิน ส่วนขั้นตอนแจ้งเหตุ/ถ่ายภาพ/เคลมต้องตรวจทั้งชุดกับแหล่งข้อมูลที่รับผิดชอบก่อนเผยแพร่ ไม่ถือว่าประโยคตัวอย่างนี้รับรองขั้นตอนทั้งหมดแล้ว
