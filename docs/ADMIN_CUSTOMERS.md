Manual entry is the primary workflow:

- Customer: Thai/English names, preferred name, birth date, nationality,
  occupation, telephone/email/LINE, contact preference/time/language, address,
  source, notes, retention review date and Active/Archived status.
- Policies: multiple policies from CoverMate or elsewhere, insurer, plan,
  number, type, status, agent, holder, insured, payer, beneficiaries, policy dates,
  premium/frequency/next due date, renewal, insured sum, IPD/OPD/room limits,
  deductible/co-pay, vehicle details, riders, coverage, exclusions and notes.
- Consent: manual evidence, notice version and exact notice text, response date,
  channel, scope and Granted/Withdrawn/Declined. Append-only changes preserve the
  earlier record. This records evidence; it does not certify its legal validity.
- Identity: one current National ID or Passport, expiry, masked display,
  owner-confirmed full reveal and a recorded access event.
- Documents: PDF/JPEG/PNG up to 2 MiB, category, related policy and notes.
  Upload/download are unavailable until the private store is configured.
- Service history: manual consultation, quote, renewal, claim or change request;
  reference, date, status, follow-up date, policy link and notes.
- Cases: create a manual case from the customer or link an existing case. The
  Case detail can open its linked customer or prefill a new customer form.

Names and at least one contact method are required. Creating a customer also
requires recorded Granted profile consent. Exact phone/email/LINE matches show
a duplicate warning; an owner can deliberately create a separate person. This
is not fuzzy matching, identity verification or an automatic merge workflow.

The registry has search, Active/Archived/All filters and 20 rows per page.
Optional form groups are disclosures; required policy fields stay visible.
Unsaved changes require confirmation before navigation. Failed saves retain
input; a version conflict offers an explicit reload after discarding the draft.
Dates and numeric values remain manual, optional unless marked required.
Service follow-up dates are records, not notification schedules. Use Cases for
existing scheduled follow-up behavior.

## Data and permissions

All routes require a verified active allowlisted owner. Browser role state is
not authorization. UAT-only admins cannot access production namespaces.
Firestore's existing catch-all denies direct client reads/writes of all customer
collections and subcollections; Admin SDK writes are authorized by the API.

Production uses `customers/{id}`; UAT uses `customersUat/{id}`. Each root has
profile, code, version, consent ledger, timestamps and creation fingerprint.
Subcollections are `policies`, `services`, `documents` (metadata only),
`private/identity`, `activities` and `mutations`. Files never enter Firestore or
the public Cloudinary CMS library. Customer data is not cached in localStorage,
CMS state, analytics or offline fallbacks.

Every mutation requires `Idempotency-Key`; existing records additionally require
`expectedVersion`. Transactions preserve revisions and audit events. Mutation
receipts never contain decrypted identity numbers or document bytes. Identity
reveal and document download recheck current consent on every retry and commit
an access event before responding. Profiles can be archived even after profile
consent is withdrawn, but other profile edits require current profile consent.
Policy writes require policy consent; identity writes/reads require identity
consent; document upload/download require document consent and additionally
identity consent for Identity-category documents. Historical records remain
visible to the owner after withdrawal so the owner can handle retention/erasure.

`contactLeads{Uat}/{id}.customerId` links a Case without replacing `caseRecord`,
the original submission, consent receipt or legacy fields. Existing Case edits
preserve this sibling field. A Case already linked elsewhere cannot be silently
reassigned. A new customer from a Case still needs separate manual Consent;
website enquiry consent is never fabricated into registry consent.

## Private GCS setup (not activated)

The owner chose private Google Cloud Storage, with **setup only if billing is
required**. No billing activation, bucket creation or production upload is
authorized by this code change. Before enabling real documents:

1. Have the owner approve the billing/storage plan. Provision separate production
   and UAT buckets; select the location and retention settings deliberately.
2. Enforce public access prevention and uniform bucket-level access. Do not grant
   `allUsers`/`allAuthenticatedUsers`, Firebase download-token access or public
   URLs. No browser CORS policy is needed because only the server accesses GCS.
3. Grant the existing server service account bucket metadata read and object
   create/get permissions, scoped to these buckets. Do not grant public access
   or unrelated project-wide storage administration.
4. Configure server-only `COVERMATE_CUSTOMER_DOCUMENT_BUCKET` and
   `COVERMATE_CUSTOMER_DOCUMENT_BUCKET_UAT`. Never point both at a public CMS
   bucket. The adapter checks enforced public-access prevention and uniform
   access before real storage operations.
5. Configure a secret `COVERMATE_CUSTOMER_VAULT_KEY`: 32 random bytes encoded as
   64 hexadecimal characters. Keep it out of source control and the browser.
   Use separate deployment secrets for UAT/production. Identity entry also needs
   this key; regular customer/policy/service records do not.
6. Verify in UAT: owner upload/download byte match, absent public access, no
   permanent share URL, missing permissions/key fail closed, withdrawal denial,
   denied non-owner access, activity entry and environment isolation.
7. Establish encrypted backup/restore and a retention/erasure procedure before
   collecting real documents. Existing CMS backup does not back up this registry
   or GCS. Keep the encryption key recoverable separately. **Do not simply rotate
   or replace it:** existing ciphertext needs an explicit re-encryption migration.

Objects are immutable encrypted JSON envelopes at a namespace/customer/document
key, with AES-GCM authenticated context. The request fingerprint determines the
object ID, so a retry does not overwrite another file. Firestore commits metadata
only after the object write succeeds. If upload succeeds but the transaction
ultimately fails, an encrypted orphan may remain; no record/download URL becomes
visible. Reconcile unreferenced objects under an approved retention/cleanup
procedure; never automatically delete potentially retained customer documents.

Provider references:
[GCS upload preconditions](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/insert),
[public access prevention](https://docs.cloud.google.com/storage/docs/public-access-prevention).

## Verification and limits

- `npm run check:customers`: shared validation, scoped consent, encryption,
  tamper/context rejection, file types and generated client parity.
- `npm run check:customers:api`: real isolated Auth/Firestore/API transactions,
  deny-by-default client rules, UAT isolation, idempotency/conflicts, profile and
  policy/service CRUD, duplicate detection, masked identity, scoped withdrawal,
  document roundtrip, case links, browser create/edit/reopen and screenshots.
  The object store is explicitly an **emulator-only in-memory test adapter**;
  it exercises encryption/consent/metadata, not a live GCS bucket.
- `npm run preview:customers`: loopback-only actual emulator API demo with
  synthetic records and a visible Local preview banner. No cloud storage is
  enabled. Requires Java 21; local auth expires after one hour. Restarting an
  unexported emulator session discards these demo records.
- Current visual evidence: `uat-results/customers/`; review screenshots with the
  full shell and desktop/mobile context. Evidence is local, not production.

The current small-owner dataset is read before filtering; there is no indexed
search engine or constant-cost query claim. Child records are read in full;
the activity display shows the newest 100. Consent history is bounded by both
200 events and a 500 KB budget to protect Firestore's root-document limit.
No automatic marketing, insurer integration, document OCR/malware scanner,
automatic renewal notifications, bulk export, hard delete, merge or automated
data-subject erasure workflow is introduced. Files are validated by signature,
not scanned for malware. Review/scan externally before opening downloaded files.
Real GCS access, production secrets, backup/restore and physical device keyboards
remain unverified until an explicitly authorized activation pass.
